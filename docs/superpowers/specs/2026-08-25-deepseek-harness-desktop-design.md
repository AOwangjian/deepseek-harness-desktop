# DeepSeek Harness Desktop 设计说明

## 1. 项目目标

打造一个面向 Windows 的 DeepSeek Harness 桌面客户端。用户双击应用后即可进入 Harness Web UI，无需手动打开终端、执行 `dsh web` 或访问浏览器地址。

首版只交付 Windows，但系统能力必须通过平台适配层隔离，为未来支持 macOS 和 Linux 保留清晰扩展边界。

项目名称与公开仓库名统一为 `deepseek-harness-desktop`。公开仓库默认只允许仓库所有者及明确授权的协作者写入，不额外授予其他用户写权限。

## 2. 产品原则与范围

桌面端采用“轻量薄壳”设计：完整承载 `dsh web` 提供的原始页面，只补充桌面系统能力，不复制、不修改 Harness 的业务界面。

### 2.1 桌面端负责

- 检测 Node.js、npm 和 `@deepseek-ai/dsh`。
- 在用户明确授权后自动安装或升级依赖。
- 启动、停止、重启和监控 `dsh web`。
- 内嵌本机 Harness Web UI。
- 提供托盘、开机自启、单实例、日志和诊断能力。
- 管理桌面端自身更新，并与 Harness 更新解耦。

### 2.2 Harness 原样负责

- 对话与会话。
- 插件管理。
- 模型及 Harness 自身设置。
- Harness Web UI 内的其他现有或未来功能。

桌面端不得依赖 Harness 的内部 DOM、组件树或前端路由，不向页面注入业务脚本。Harness 升级后，桌面端原则上只需重启服务并重新加载页面。

## 3. 技术选型

采用 Electron、React 和 TypeScript。

选择依据：

- 与 Harness 的 Node.js/npm 生态一致，依赖与进程管理路径直接。
- Electron 对托盘、自启动、安装包和跨平台支持成熟。
- 能可靠承载现有 Web UI，并为未来 macOS/Linux 版本复用主要代码。

Windows 首版使用 Electron Builder 生成安装版和便携版。平台相关功能通过接口隔离，Windows 适配器不得渗透进通用服务层。

## 4. 系统架构

系统分为四层：

1. 桌面呈现层：React + TypeScript，显示状态栏、安装向导、诊断页和桌面设置，并承载 Harness 页面。
2. 应用控制层：协调启动状态机、窗口、托盘、更新和错误恢复。
3. Harness 管理层：负责依赖检测、安装、版本查询、子进程生命周期、健康检查和日志采集。
4. 平台适配层：封装自启动、进程树终止、系统通知和平台路径等操作。首版实现 Windows 适配器。

Electron 主进程负责系统能力和生命周期，渲染进程不得直接访问 Node.js。主进程与渲染进程之间只通过范围明确、可验证的 IPC 接口通信。

## 5. 用户界面

Harness Web UI 占据主窗口绝大部分空间。桌面端只增加窄状态栏，用于展示服务状态、版本、日志入口、重启入口和桌面设置入口。

关闭主窗口时默认最小化到系统托盘。托盘菜单提供：

- 打开主窗口。
- 启动、停止和重启 Harness。
- 查看日志。
- 打开桌面设置。
- 彻底退出。

桌面设置只管理桌面行为，例如开机自启、关闭行为、更新策略和日志保留；模型、插件与对话设置继续由 Harness 原界面管理。

## 6. 依赖安装与升级

应用启动后检测 Node.js、npm、`dsh` 及其版本。缺少依赖时进入安装向导，提供三个明确选项：

1. 自动安装：展示待安装内容、准确版本、来源和预期位置，用户确认后执行。
2. 手动安装：展示官方链接与可复制命令，用户完成后点击“重新检测”。
3. 暂不安装：进入受限模式，仅保留诊断和设置能力。

Windows 自动安装 Node.js 时优先使用可信的系统包管理通道；通道不可用时转为手动引导，不下载来源不明的安装器。安装 `dsh` 时使用 npm 官方注册表中的 `@deepseek-ai/dsh` 包，并在执行前显示目标版本。

升级不得静默执行。桌面端检测到新版本后，由用户选择自动升级或稍后处理。升级失败时保留或恢复当前可用版本。

## 7. 启动与生命周期

1. 应用读取桌面配置并完成依赖检测。
2. 选择空闲本机端口。
3. 使用参数数组启动 `dsh web --no-open --port <port>`，不拼接 shell 命令。
4. Harness 只绑定本机回环地址。
5. 桌面端执行健康探测，服务可访问后才加载页面。
6. 页面连接中断时先自动恢复；连续失败后进入诊断页。
7. 用户彻底退出时先正常终止子进程，超时后清理该子进程树。

应用使用单实例锁。每个由桌面端启动的 Harness 进程都关联实例标识和可验证元数据，只管理本应用创建的服务，不影响用户在终端中启动的其他 `dsh` 进程。

应用异常退出后再次启动时，只回收能够确认属于上次桌面会话的遗留进程。

## 8. 异常处理

- 依赖缺失：进入安装向导。
- 自动安装不可用或失败：保留完整错误摘要并切换到手动安装路径。
- 端口冲突：重新选择空闲端口并重试。
- 启动超时或进程崩溃：显示最近日志、重试、复制诊断报告和打开日志目录。
- 页面断连：短时自动重连，超过阈值后进入诊断页。
- Harness 升级失败：继续使用升级前的可用版本。
- 桌面端更新失败：不影响现有桌面端和 Harness 的继续使用。

日志与诊断报告默认过滤 API Key、Token、Authorization 请求头等敏感信息，且不包含用户对话正文。

## 9. 安全边界

- Electron 启用上下文隔离并关闭渲染页面的 Node 集成。
- 页面只允许加载经过校验的本机 Harness 地址。
- 未知导航、弹窗和外部协议必须被拦截或交由系统浏览器显式处理。
- IPC 参数使用运行时校验，不暴露通用命令执行接口。
- 外部进程使用可执行文件与参数数组启动，不通过字符串拼接进入 shell。
- 依赖安装和升级均需要用户明确授权。
- 发布流水线不得在日志或产物中泄露签名密钥及其他凭据。

## 10. 发布与更新

GitHub Actions 在 Windows 环境执行类型检查、测试和打包，并将安装版与便携版发布到 GitHub Releases。

桌面端更新流程为：检测版本、展示版本信息、用户确认、下载并安装。Harness 更新与桌面端更新分别检测和执行，互不捆绑。

如果首版没有代码签名证书，安装时可能触发 Windows SmartScreen 的“未知发布者”提示。正式面向大量用户分发前，应配置受信任的 Windows 代码签名证书。

## 11. 测试策略

### 11.1 单元测试

- 依赖与版本检测。
- 安装选择及状态机转换。
- 空闲端口选择和冲突重试。
- 命令参数构造与输入校验。
- 日志敏感信息过滤。
- 平台适配接口的通用行为。

### 11.2 集成测试

- 模拟 Harness 正常启动、超时、崩溃和断连。
- 子进程正常退出、强制清理及遗留恢复。
- 安装成功、取消、失败和升级回滚。
- 单实例、窗口关闭和托盘行为。
- Harness 页面加载白名单与未知导航拦截。

### 11.3 打包验收

- 在干净 Windows 环境验证安装版和便携版。
- 覆盖无 Node.js、已有 Node.js、已有旧版 `dsh` 三种环境。
- 验证用户无需打开终端或外部浏览器即可完成安装选择并进入 Harness UI。

## 12. 验收标准

- 用户双击桌面应用后可进入原始 Harness Web UI。
- 依赖缺失时，用户可自行选择自动安装、手动安装或暂不安装。
- 自动安装和升级执行前均展示来源、版本并取得确认。
- 主窗口关闭后可按设置进入托盘，彻底退出后不遗留本应用创建的 Harness 进程。
- Harness 内部功能升级不要求桌面端同步重写界面。
- 故障时提供可操作的诊断信息，同时不泄露密钥或用户对话。
- Windows 首版可安装、可卸载、可使用；架构允许未来增加 macOS/Linux 平台适配器。

## 13. 首版明确不做

- 重写 Harness 的对话、会话、插件或模型设置界面。
- 修改或注入 Harness Web UI。
- 默认开放局域网或远程访问。
- 未经确认静默安装、静默升级依赖。
- 首版交付 macOS 或 Linux 安装包。
